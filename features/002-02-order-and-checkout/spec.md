# Feature: Create orders and hosted checkout

**Branch**: `002-02-order-and-checkout` · **Status**: clarified

## Summary

An authenticated caller can create a durable order for one product, initiate Stripe-hosted Checkout, and inspect the order's status and chronological payment history. Repeated requests, interrupted calls, and uncertain Stripe outcomes preserve one logical checkout operation and an inspectable local identity. Checkout creation does not confirm payment; card entry stays on Stripe's page.

## Acceptance Scenarios

1. **AS-01 — Durable order and checkout.** Given an authenticated caller and valid description, integer minor-unit amount, and request idempotency key, when the caller requests creation, then the backend generates an order ID, persists the purchase details using its configured currency, associates a durable checkout operation with that order, and exposes the hosted checkout location when creation succeeds. Session creation does not mark the order paid. The order contains one product, without quantities or order line items. Source: supplied checkout feature; F-01, E-01.
2. **A-03 — Repeated and overlapping creation.** Given the same logical creation request and key, when identical requests are repeated or deliberately submitted concurrently, then they resolve to one durable order/checkout operation. Changed inputs under that key are rejected. The uniqueness guarantee holds across independent PostgreSQL connections/processes. Source: F-03, E-01, E-09, Q2/Q4.
3. **AS-02 — Intentionally separate orders.** Given identical descriptions and amounts but different keys for intentionally new orders, when creation is requested, then those requests may represent distinct orders. Keys must not be derived solely from purchase fields. A fresh key targeting the same order does not permit a duplicate active checkout or another charge for a paid order. Source: supplied checkout feature; F-03.
4. **A-06 — Stripe response lost.** Given a persisted local operation, Stripe key, and parameters, when Stripe processes creation but its response is lost, then retry/recovery uses that same operation, key, and parameters without duplicate creation. Its unresolved outcome remains inspectable through a local identifier until established. Correlation does not depend solely on saving the Stripe response. Source: F-03, F-06; controlled failure injection required by E-05/Q3.
5. **A-07 — Stripe remains unavailable.** Given an accepted durable checkout operation and unavailable Stripe, when creation cannot establish an outcome within the configured time budget, then the request finishes within that budget, retains an unresolved integration outcome rather than confirmed business failure, and returns a local identifier usable to inspect status/history without starting another operation. Source: F-02, F-06, E-03.
6. **A-08 — Restart before local result commit.** Given Stripe creation succeeds, when the process stops before the result commits locally, then restart and retry/recovery preserve the original operation identity, Stripe key, and parameters without creating another logical checkout. This includes a result lost before the Stripe object ID is saved. Source: F-03, F-06, F-07, Q3. The manual reconciliation command is a later feature.
7. **A-02 — Nonpayment and permitted continuation.** Given a declined attempt or abandoned/cancelled browser flow, when status is inspected or a later supported attempt is requested, then the order is not marked paid and those events do not imply a terminal failure for the entire order. A later successful attempt remains possible where Stripe's supported lifecycle permits it. Payment confirmation itself belongs to the webhook/reconciliation features. Source: F-02, F-05; continuation follows the Checkout contract below.
8. **AS-03 — Authenticated inspection.** Given an existing local order/operation, including an unresolved creation, when an authenticated caller requests status and history, then the service exposes current payment status and relevant chronological history, distinguishing confirmed payment, unpaid/pending work, and an unresolved integration outcome. Browser presentation is outside this feature. Source: supplied checkout feature; F-02, F-08.
9. **A-12 — Unauthorized and invalid requests.** Given missing/invalid authentication or invalid monetary/request input, when introduced service operations are requested, then unauthorized access and invalid input are rejected. Logs and stored history exclude secrets, card numbers, CVCs, and unnecessary personal data. Existing authentication runs before protected handler body parsing/side effects. Source: E-01, E-02, E-04, Q5.
10. **AS-04 — Transactional operation history.** Given a persisted business change and its corresponding audit entry, when the transaction commits, then both are durable; an injected transaction failure leaves neither partially committed. Relevant history is append-only through normal application paths. Source: F-08, E-01, Q2.
11. **A-11 — Creation outside the safe retry window.** Given an unresolved creation older than Stripe's safe idempotency retry window, when retry is considered, then the service does not blindly issue another creation because an object ID/result is missing. The operation remains explicitly unresolved when evidence cannot establish its outcome; the later reconciliation feature reports it for investigation. Source: F-06, F-07, Q3.
12. **A-18 — Concurrent feature entry points.** Given deliberately coordinated overlapping creation requests through independent database connections, when they execute, then PostgreSQL preserves payment uniqueness and valid state, and affected shared-state paths pass race detection. Webhook/reconciliation overlap joins this guarantee in their later features. Source: E-05, E-09, Q4.

## Edge Cases

- Missing, invalid, or unsupported description/amount/request-key inputs and over-limit bodies must be rejected according to the clarified input contract; the Checkout contract below defines exact validation, encoding, and responses. Money uses integer minor units and the backend-configured currency, never floating point.
- One request key with changed purchase/operation parameters is rejected, including concurrent conflicting submissions. An identical replay after response loss or restart preserves the existing association.
- Identical purchase fields are insufficient to identify a logical request: deliberately separate orders use different random request keys.
- A new request key for an existing order cannot bypass the duplicate-active-checkout or already-paid protections. Permitted later attempts are distinct durable operations on that same order, with lifecycle eligibility defined by the Checkout contract below.
- Network timeout, definitive validation failure, card decline, and indeterminate Stripe server error need distinct retry/outcome policies. A timeout or unknown server outcome cannot alone establish confirmed business failure.
- Interruption before receiving an external response and after Stripe success before local commit must leave recoverable correlation even without a saved Stripe object ID.
- Database constraints/transactions must preserve invariants with independent concurrent processes; a process-local mutex is insufficient. A failed business/history transaction cannot leave a partial effect.
- Checkout creation, browser cancellation, abandonment, and browser return URLs are not payment confirmation. A delayed failure cannot regress confirmed successful payment.
- Retry beyond Stripe's retention guarantee cannot be justified solely by missing local evidence.
- Authentication rejection and existing foundation deadlines/shutdown behavior remain applicable to introduced operations. Exact probes remain public under their existing contract.

## Functional Requirements

1. **FR-001 — Purchase model.** The system MUST support one merchant, one Stripe sandbox account, one configured currency, and one-time card payments with immediate capture through Stripe-hosted Checkout. Each order MUST represent one product with an authenticated user-entered description and amount, without quantity, cart, order line items, catalog, or inventory. Card entry MUST stay on Stripe's page. Sources: feature purpose/behavior; F-01; application scope.
2. **FR-002 — Authoritative purchase data.** The system MUST accept description, amount, and a request idempotency key; generate the order ID on the backend; validate and durably store the accepted purchase details; and use the configured currency. The accepted persisted amount and currency MUST be authoritative and fixed for the payment operation. Payment attempts/history MUST remain associated with that order. Sources: F-01, E-01; supplied feature.
3. **FR-003 — Monetary/input correctness.** The system MUST use integer minor units with explicit currency, reject invalid/out-of-range amounts and unsupported currencies, validate description/request inputs, and limit request body sizes. Runtime configuration MUST use validated environment settings and sandbox credentials/objects. The Checkout contract below defines currency, ranges, description/key constraints, body limits, and API encoding. Sources: E-01, E-02, Q5; supplied feature.
4. **FR-004 — Caller protection.** The system MUST authenticate order creation, checkout operations, status, and history using the established HTTP Basic authentication boundary. Unauthenticated callers MUST NOT create orders or set prices; authentication MUST precede protected routing/body parsing/side effects. Preserve existing authentication, exact public health/readiness probes, request correlation, and shutdown admission/deadlines. Sources: E-02, application instructions, supplied feature prerequisite.
5. **FR-005 — Checkout result.** The system MUST expose the hosted checkout location on successful creation and MUST NOT mark the order paid merely because a session was created or a browser returned. Confirmed payment requires verified evidence correlated with the correct order/operation and expected amount/currency. Webhook/evidence processing is later scope. Sources: F-01, F-05; core journey; supplied dependency features.
6. **FR-006 — Durable request association.** The system MUST durably associate the browser-to-backend request key with submitted data and resulting order/operation, enforcing uniqueness in PostgreSQL. Identical repetitions, retries, lost-response retries, and concurrent submissions MUST produce one logical order/checkout operation. Reusing that key with different inputs MUST be rejected. Sources: F-03; supplied feature.
7. **FR-007 — Distinct identities.** The system MUST distinguish the browser request key from the backend Stripe checkout key. The browser request has no backend order ID yet. The backend Stripe key MUST identify a durable checkout operation associated with the generated order ID; same-mutation retries MUST reuse it. A supported later checkout attempt MUST be a distinct operation on the same order. Sources: F-03; supplied feature.
8. **FR-008 — Parameter binding.** The system MUST persist/compare operation parameters separately and reject changed inputs under an existing key. It MUST NOT encode amount into an idempotency key or derive a request key solely from description/amount; identical purchase data may belong to intentionally separate orders. The exact Stripe key string format is not prescribed. Sources: F-03; supplied feature.
9. **FR-009 — External mutation prerequisite.** The system MUST persist local operation identity, the Stripe idempotency key, and its parameters before issuing the Stripe mutation. Correlation MUST NOT depend solely on successfully saving the Stripe response. Sources: F-03, F-06; supplied feature.
10. **FR-010 — Safe retry/restart.** The system MUST preserve the same durable operation, Stripe key, and parameters across bounded retries, response loss, interruption, and process restart. Recovery MUST cover interruption before receiving the response and after Stripe success before local result commit, including no saved Stripe object ID, without duplicate creation. Sources: F-03, F-06, Q3; A-06/A-08.
11. **FR-011 — Call/retry bounds.** The system MUST give Stripe calls explicit bounded execution time and retryable failures bounded retries with backoff, limiting both attempts and elapsed time. Context cancellation/deadlines MUST propagate through external calls, database operations, and owned work. Preserve foundation shutdown: configurable 10-second default grace, 5-second default cleanup, 15-second default total bound, and nonzero exit on cleanup failure. The Checkout contract below defines feature-specific request/call/retry budgets. Sources: F-06, E-03, Q3/Q4.
12. **FR-012 — Failure classification.** The system MUST distinguish network timeouts, definitive validation failures, card declines, and indeterminate Stripe server errors rather than give them one retry/state-transition policy. If Stripe processing cannot be established, it MUST retain an unresolved outcome instead of reporting confirmed business failure. Sources: F-06; supplied feature; Q3.
13. **FR-013 — Inspectable ambiguity.** The system MUST return a local identifier usable to inspect accepted unresolved work without starting a new operation. Unavailable Stripe MUST lead to a bounded response exposing that inspectable unresolved operation. Sources: F-02, F-06; A-07.
14. **FR-014 — Status/history service.** The system MUST provide authenticated service access to current status and chronological relevant history. Callers MUST distinguish confirmed payment, unpaid/pending work, and unresolved integration outcomes. A decline, abandonment/cancellation, or timeout MUST NOT imply confirmed terminal failure of the entire order. Browser presentation is later scope. Sources: F-02; supplied feature.
15. **FR-015 — Lifecycle protections.** The system MUST prevent duplicate active checkout and charging a paid order again, even with a fresh request key for that order. Supported later attempts MUST remain possible where Stripe's Checkout lifecycle permits them. Confirmed successful payment MUST NOT regress due to delayed failure evidence. The Checkout contract below defines states, eligibility, and representation. Sources: F-03, F-05; supplied features 2/3/5.
16. **FR-016 — Durable audit data.** The system MUST persist order ID, description, amount/currency, local operation identities, relevant Stripe object/event identifiers as available, timestamps, relevant local operations, state changes, and recovery outcomes. History MUST be sufficient to reconstruct the current state and append-only through normal paths; storing every raw Stripe payload is not required. Sources: F-08; supplied feature.
17. **FR-017 — Atomic history/state.** The system MUST commit each local business change and its corresponding history entry in the same PostgreSQL transaction. A failed transaction MUST leave neither partially committed. Shared transition semantics MUST permit later confirmation/recovery to apply one transition/history entry exactly once and observe existing results without regression. Sources: F-08, E-01, E-09, Q2; dependency features.
18. **FR-018 — Database concurrency.** The system MUST enforce critical uniqueness/consistency and valid payment transitions through PostgreSQL constraints/transactions across independent connections/processes. Correctness MUST NOT depend solely on process-local locks. Schema changes MUST use versioned migrations. Sources: E-01, E-09, Q2/Q4; supplied feature.
19. **FR-019 — Recovery evidence and safe age.** The system MUST preserve durable evidence for later manual reconciliation, including creation with no saved Stripe object ID. It MUST NOT blindly repeat an old creation beyond Stripe's idempotency retention guarantee. Insufficient evidence MUST leave the operation explicitly unresolved for investigation. The manual command, selection/worker behavior, and full evidence recovery are later scope. Sources: F-06, F-07, Q3; supplied feature/dependency feature 5.
20. **FR-020 — Data minimization.** The system MUST keep secrets, card numbers, CVCs, and unnecessary personal data out of logs/history; privileged service credentials MUST NOT appear in browser-delivered code or Stripe requests. Feature operations MUST NOT expose prohibited data in responses. Sources: E-02, Q5; application instructions.
21. **FR-021 — Visibility.** The system MUST produce structured sanitized logs with request/operation correlation identifiers and useful error context for introduced operations/failures. Preserve health/readiness behavior; verify it when dependency readiness changes. Sources: E-04, Q6; application instructions.
22. **FR-022 — Shared engineering behavior.** The system MUST use explicit error handling and context propagation, keep payment rules independently testable from HTTP/Stripe integration, keep SQL/SDK details in integration packages, and avoid unnecessary abstractions/services. Owned concurrent work MUST have a bounded lifetime and cancellation/completion path with synchronized shared state. Sources: E-03; application instructions; Q4/Q6.

## Checkout contract

### Input and configuration

- V1 uses USD cents. `PAYMENT_CURRENCY` defaults to `usd` and accepts only that exact value. `PAYMENT_MIN_AMOUNT` defaults to `50`; `PAYMENT_MAX_AMOUNT` defaults to `100000`. Both are base-10 integers satisfying `50 <= min <= max <= 100000`. The upper bound is an application sandbox limit, not Stripe's maximum. Invalid configuration prevents HTTP serving without exposing values. Persisted purchase data survives configuration changes: replay compares against stored inputs and does not reprice or invalidate an accepted amount because bounds changed.
- A creation body has exactly `description`, `amount`, and `request_key`. Description is valid UTF-8, 1–200 Unicode code points, contains no Unicode control characters, and has no leading/trailing Unicode whitespace. Preserve accepted text exactly without trimming, case folding, or normalization. Amount is a positive signed-64-bit JSON integer token containing decimal digits only, within configured bounds; strings, fractions, exponents, null, booleans, overflow, and currency fields are rejected. No client currency or price override is accepted.
- `request_key` is a canonical lowercase hyphenated UUID v4, generated once per intended request. The backend generates distinct random UUID v4 order/operation IDs and an independent Stripe key of at most 255 characters. Request keys are globally unique for this single merchant and bind to method, logical target, and accepted purchase data. A key cannot be reused across initial creation and continuation, or across different orders. Local bindings have no automatic expiry/deletion in v1. Validate replay syntax first, resolve its key binding, and compare stored inputs before applying current configurable amount limits to genuinely new orders; changed inputs return conflict.
- Authenticate before protected routing/parsing. POST bodies require `application/json` (optional UTF-8 charset), at most 4096 bytes of decoded JSON source including whitespace, one object, exactly the declared fields once, and EOF after trailing whitespace. Reject duplicate/unknown fields, malformed UTF-8/JSON, omitted/null values, arrays, extra JSON values, and unsupported content encodings. GET/HEAD endpoints reject any body using bounded detection. Query parameters are rejected except the declared history pagination fields. Invalid requests cause no order/operation/history/Stripe effect.
- `STRIPE_SECRET_KEY` must have the `sk_test_` prefix and a nonempty suffix, with no surrounding whitespace or Unicode control characters; other key classes and live keys prevent HTTP serving. `APP_BASE_URL` defaults to `http://localhost:8080`; accept an absolute HTTP origin with host `localhost`, `127.0.0.1`, or `[::1]`, optional valid port, and no credentials/path beyond `/`, query, or fragment. These serving settings are unnecessary for local `migrate`/`probe` commands. Settings are fixed for each process; secrets are never returned/logged. Sandbox object evidence must have `livemode=false`.

### Authenticated HTTP API

| Method and path | Input | Result |
| --- | --- | --- |
| `POST /api/orders` | Creation body | Atomically accept an order, initial operation, key binding, and history, then attempt Checkout creation. |
| `POST /api/orders/{order_id}/checkout` | Exactly `{"request_key":"<uuid>"}` | Continue the current operation or create an eligible distinct attempt with the order's immutable purchase data. |
| `GET /api/orders/{order_id}` | No body/query | Read local purchase, payment status, current operation, and continuation/investigation flags; never call Stripe or mutate state. |
| `GET /api/orders/{order_id}/history?after=<sequence>&limit=<count>` | Optional `after` nonnegative decimal signed-64-bit integer, default `0`; `limit` integer 1–100, default `50`; fields once | Read entries in ascending per-order sequence strictly after the cursor. Return at most limit entries and `next_after` equal to the last returned sequence (the input cursor if empty). |

- Canonical UUID paths are required; malformed IDs return `400`, unknown orders `404`. HEAD is supported on GET paths with identical status/headers and no body. Known paths with other methods return `405` and `Allow`; unknown paths return `404`. Existing Basic-auth `401` and public probe/shutdown responses retain their established contract.
- Feature API responses use JSON UTF-8, `Cache-Control: no-store`, and existing `X-Request-ID`. POST responses and order reads use an `order` object (`id`, `description`, `amount`, `currency`, `payment_status`, `created_at`, `updated_at`) and an `operation` object (`id`, `state`, nullable `stripe_session_id`, nullable `stripe_payment_intent_id`, nullable `checkout_url`, nullable `first_dispatch_at`, nullable `expires_at`, `created_at`, `updated_at`, nullable `failure_code`, `investigation_required`). Top-level flags are `can_resume`, `can_retry_same_operation`, and `can_start_new_attempt`. A replay/continuation response refers to its bound operation even if a newer operation exists; an order read refers to the current operation. Timestamps use UTC RFC3339 with fractional seconds allowed. Nullable fields are explicit JSON null. Raw Stripe bodies, secrets, and customer/card data are never returned.
- The flags describe permitted actions, not guaranteed Stripe outcomes. For an unpaid order, `can_resume` requires the referenced operation to be open with a saved URL and a future saved expiry. `can_retry_same_operation` requires prepared work, or unresolved work with a supported stored snapshot and either a known session ID or time strictly before first_dispatch_at + 23h; mismatched evidence and unsupported snapshot versions make it false. `can_start_new_attempt` requires the current operation to be confirmed rejected without prior ambiguity or verified expired/unpaid, with no other potentially active operation. All three are false for paid orders. On reads these are last-observed local eligibility; POST rechecks Stripe evidence and the transactional paid/current-operation guard. When wire-attempt/time budget is exhausted after verifying eligibility, a durably prepared new operation returns `202` and its bound key can dispatch it later without another operation.
- A new durable operation with a usable Checkout result returns `201`; an identical replay or continuation with an established result returns `200`. Accepted prepared/unresolved/in-flight work returns `202` with the same envelope and local IDs, `Location: /api/orders/{id}`, and `Retry-After: 1`. A concurrent duplicate may immediately return that inspectable `202`; it cannot allocate another operation. Initial durable acceptance is committed before external work; if later result persistence fails, report `202` when a database read can establish those IDs, otherwise `503` with the same known IDs when available. Never claim success from an uncommitted result.
- Errors use `{"error":{"code":"<stable-code>","message":"<generic-message>"}}`, adding known `order_id`/`operation_id` inside `error` for accepted work. Use `400 invalid_request` for validation/body-read failure while a response is possible, `413 body_too_large`, `415 unsupported_media_type` (including content encoding), `404 not_found`, `405 method_not_allowed`, `409 idempotency_conflict` for changed bindings, `409 checkout_blocked` for a fresh-key request when an attempt is unsafe, `502 checkout_rejected` for a confirmed Stripe creation rejection, and `503 temporarily_unavailable` for inability to durably accept/read work. Messages never copy submitted bodies or Stripe/internal error text. Fresh-key blocked requests create no binding/operation; callers may retry that key once eligibility is established. A definitive rejection replay returns the same rejection and IDs, without another Stripe POST.
- History returns `{"order_id":"<uuid>","entries":[...],"next_after":<sequence>}`. Each entry has `sequence`, `kind`, `recorded_at`, `order_id`, nullable `operation_id`, nullable `from_state`/`to_state`, nullable Stripe session/PaymentIntent/event/request IDs, and nullable stable `failure_code`. Kinds are `order_created`, `operation_prepared`, `dispatch_started`, `operation_state_changed`, `payment_confirmed`, and `recovery_recorded`. Sequence is strictly increasing per order; timestamps order observations, not purported external causality. Store relevant external event time separately when present. Reads, identical replay, and unchanged observations add no duplicate business-transition entry; later features may record deduplicated recovery observations. History is never updated/deleted through normal application paths.

### Orders, operations, and continuation

- Order `payment_status` is `unpaid` or `paid`; `paid` is terminal for v1. An integration problem belongs to the operation and does not make the whole order terminally failed. Initial unpaid orders always have a durable current operation.
- Operation states: `prepared` (durable intent, no dispatch marker), `unresolved` (dispatch may have executed or evidence is insufficient), `open` (verified usable unpaid Checkout), `complete_unpaid` (verified complete session whose payment is not confirmed), `expired` (verified expired/unpaid session), `rejected` (confirmed creation rejection before any possible successful creation), and `paid` (confirmed, correctly correlated payment). First dispatch changes prepared to unresolved with history before the call. An interruption at that boundary remains unresolved even if the call never actually ran.
- An open session supports further card entry/decline recovery on the same hosted page. Browser cancellation, abandonment, card-decline observations, and local passage of `expires_at` do not prove expiration or permit replacement. Return `can_resume=true` and its saved URL only while locally open and before its saved expiry; at/after expiry suppress the URL and require evidence refresh. Every resumed POST with a known session ID retrieves its current Stripe state within budget before returning a usable URL. GET reads report last verified local state and never assert that stale observations are current Stripe state.
- A new-key continuation on prepared/unresolved work binds to and retries the same operation where safe; it never allocates another operation. An open operation is retrieved and resumed under its same identity. If retrieval establishes expired/unpaid, the request may allocate one new operation only after the atomic order guard below; the new key binds to that new operation. Same-key replay always targets its original operation and never creates a later one. Complete_unpaid, paid, mismatched/unknown evidence, failed retrieval, and old ambiguous creation reject a fresh-key attempt with `409 checkout_blocked`. Paid orders block all continuation, including replays, without external mutation; initial creation-key replay only reports its existing order/result, suppressing checkout_url and setting all three continuation flags false when the order is paid even if its historical bound operation was open.
- A distinct operation is eligible only for an unpaid order after every prior potentially active operation has verified `expired` plus `payment_status=unpaid`, or a confirmed `rejected` with no prior ambiguous dispatch. Retrieve the preceding known session on a new attempt to verify its correlation, amount, currency, mode, sandbox flag, and expired/unpaid state; a local timer or absence from a list is insufficient. A rejected operation has no session to retrieve. Complete/unpaid is deliberately blocked even with a decline: processing can still complete. Explicit session expiration/cancellation APIs, automatic recovery URLs, and attempts after complete_unpaid are outside v1.
- Confirmation in Features 3/5 requires trusted Stripe evidence for a session with `mode=payment`, `livemode=false`, matching local order/operation metadata and client reference, matching associated session/PaymentIntent IDs where known, `amount_total` equal to persisted amount, currency `usd`, `status=complete`, and `payment_status=paid`. Require a nonempty PaymentIntent ID and validate it against a stored ID when one exists. Trusted evidence is a signature-verified supported session event or an authenticated Stripe retrieval, never browser data. PaymentIntent-only evidence, `no_payment_required`, unknown state combinations, and mismatches cannot establish paid or enable replacement; report investigation. Feature 2 creation/continuation does not apply paid confirmation; a retrieved paid session without local confirmation retains unresolved evidence, blocks creation, and awaits Features 3/5. Feature 3 chooses its supported event/acceptance machinery separately.
- Atomic PostgreSQL guards enforce one current potentially active operation per order, globally unique request and Stripe keys, unique associated session/payment IDs, immutable request binding/purchase snapshots, and monotonic paid state across independent connections/processes. Serialize eligibility/creation and recheck paid/current-operation state in the committing transaction. Apply order/operation changes with history atomically; stale external results cannot overwrite paid or attach a second active operation. A row lock/transaction or equivalent database mechanism is required; holding only a process-local mutex is insufficient. Network calls cannot hold a transaction open for their duration. Concurrent dispatch/recovery uses persisted coordination and the same Stripe key; losing ownership/cancellation preserves recoverability and cannot admit another attempt. Verified expiration of every earlier attempt establishes the safety of the paid guard while a later session is dispatched.

### Stripe request, deadlines, and recovery

- Persist the complete Stripe parameter snapshot and key before mutation: `mode=payment`, explicit card-only methods, one Stripe line item with fixed `quantity=1`, inline price currency/amount/product name from the accepted order, `client_reference_id=order_id`, and session plus `payment_intent_data.metadata` containing `order_id` and `operation_id`. Use immediate automatic capture. Disable automatic tax, discounts/promotion codes, adaptive pricing, and after-expiration recovery so totals/currency remain fixed. Stripe's required single line item is adapter data; the application has no cart/quantity/line-item model. Use hosted mode for the pinned SDK/API version; do not copy enum names from another version.
- Success and cancel URLs are the validated base origin plus `/?order_id=<id>&checkout_return=success` or `cancel`. They carry no credentials and remain fixed for the operation. Feature 2 returns to the existing landing page; browser presentation is Feature 4. In the pre-call transaction set immutable `first_dispatch_at` from server time and an integer Unix `expires_at` 23 hours 59 minutes later, and finalize those snapshot fields before dispatch. Neither expiry nor URLs/metadata/API version/key are recomputed on replay or process restart. Pin the Stripe SDK and its compatible API version before SDK-based test authoring and freeze those pins with reviewed tests and persist the operation's version; unsupported old snapshot versions remain unresolved rather than silently migrating parameters.
- Serving budgets are validated environment settings: `CHECKOUT_REQUEST_TIMEOUT` default `10s`, range 2–10 seconds; `STRIPE_CALL_TIMEOUT` default `2s`, range 100 milliseconds–2 seconds; `STRIPE_RETRY_BUDGET` default `7s`, range 500 milliseconds–7 seconds and no greater than request timeout minus 1 second; `STRIPE_MAX_ATTEMPTS` default `3`, integer 1–3. Call timeout cannot exceed retry budget. The retry budget is shared by all Stripe calls/waits in one request; STRIPE_MAX_ATTEMPTS bounds the total HTTP wire attempts across creation and retrieval combined in one incoming request, including SDK retries. Disable SDK automatic retries if an outer policy owns retries. The overall request deadline begins at protected handler admission and includes body reads, database work, external calls, waits, and final persistence/response; use the earlier parent cancellation/deadline. The remaining 1 second bounds final database/response work; success is not required at deadline. Configure actual body-read cancellation/deadlines, not only a context that leaves a blocking read running. HTTP read/write settings must each accommodate request timeout plus a 1-second response margin; defaults are 11s read and 15s write for serving these endpoints. Keep existing shutdown budgets and admission behavior.
- Retry waits are 250 milliseconds before attempt 2 and 500 milliseconds before attempt 3, cancellable and within remaining elapsed budget. A longer valid Stripe `Retry-After` controls the minimum wait; if it cannot fit, stop unresolved. Honor `Stripe-Should-Retry: false`. Retry transport timeout/reset, 429, and documented transient conflict/5xx only with the same snapshot/key within the safe window. A 5xx remains indeterminate even when its retries repeat a cached failure. A structured parameter-validation rejection before execution or sandbox credential/permission rejection on an operation with no earlier ambiguous dispatch is confirmed rejected, with no automatic retry; changing parameters requires an eligible distinct operation. Generic 4xx, idempotency mismatch, malformed success, missing required identifiers or an open session URL, correlation mismatch, and uncertain dependency errors remain unresolved for investigation rather than presumed safe. A rejection after any earlier uncertain dispatch cannot prove that earlier creation had no effect. Hosted card declines remain unpaid/open or complete_unpaid according to verified session evidence and never justify replaying creation under a new key.
- Same-operation POST replay without a saved session ID is allowed only while server time is strictly before `first_dispatch_at + 23h`. At that boundary or later, issue no creation POST, keep unresolved, and block replacement. Persist an ambiguity marker conservatively before each possible send; definitive no-creation classification must distinguish a fully observed first rejection from earlier interruption/lost response. Replayed Stripe responses must pass the same correlation/amount/currency validation as first responses. A known ID uses GET retrieval, which does not depend on the idempotency retention window. A saved Stripe request ID supplements metadata but is not an object lookup guarantee.
- `investigation_required` is true for unresolved work at least 15 minutes after first dispatch, exhausted safe retry age, mismatched evidence, indeterminate 5xx, incompatible snapshot versions, or confirmed configuration/integration rejection. This is an explicit advisory alongside operation state, not proof of failure and not permission for a fresh attempt. Same-key replay can still recover a network ambiguity inside the safe window. No background task starts from this flag.
- Feature 5 recovers missing IDs through trusted correlated webhook evidence or bounded session listing with a `created` interval from first dispatch minus 5 minutes to the last possible dispatch plus 5 minutes, matching metadata/client reference locally; the list API has no metadata search parameter. Limit to 10 pages of 100 results, an overall 30-second per-operation recovery budget, and the agreed per-call timeout/attempt/backoff ceilings. Cap every call/wait by the remaining budget. Exactly one correctly matched candidate must be retrieved and validated before attaching its ID/transition. Zero candidates, multiple matches, unfinished pagination/budget exhaustion, or lookup failures preserve unresolved/investigation; absence cannot prove no creation. Persist last possible dispatch time before calls for this interval. Beyond 23h use only evidence reads/verified notifications, never creation replay. Operator investigation uses sanitized local operation/Stripe request IDs and the sandbox dashboard; v1 exposes no manual force-paid/reset/recreate override. Worker/queue/shutdown settings remain Feature 5 choices.

### Stripe reference basis

- [Idempotent requests](https://docs.stripe.com/api/idempotent_requests) supports fixed key/parameter replay and states the minimum 24-hour retention; the 23-hour limit is the application's conservative cutoff.
- [Advanced error handling](https://docs.stripe.com/error-low-level) distinguishes network/content/server failures, warns that 500 responses can have side effects, and documents retry headers and metadata correlation.
- [Checkout creation](https://docs.stripe.com/api/checkout/sessions/create) defines required line items, reference fields, supported expiry bounds, and hosted return URLs. The adapter snapshot and 23h59m expiry are application contracts within those bounds.
- [Checkout Session object](https://docs.stripe.com/api/checkout/sessions/object) distinguishes open/complete/expired from paid/unpaid; complete does not by itself prove payment completion.
- [Session listing](https://docs.stripe.com/api/checkout/sessions/list) supports created-interval filtering and pagination; metadata matching and investigation limits are application policy.
- [Currency limits](https://docs.stripe.com/currencies) documents minor units and the USD minimum, which also depends on account settlement currency. Sandbox setup must support the chosen USD charge range; application validation does not guarantee every account/card accepts every amount.

## Success Criteria

- **SC-01:** An accepted valid request has durable authoritative purchase data and one checkout operation; successful creation exposes a hosted location without paid status. Sources: F-01; AS-01.
- **SC-02:** Identical repeated/overlapping requests preserve one order/operation across independent PostgreSQL connections; changed inputs under a key are rejected. Intentionally separate orders with identical purchase fields remain distinct. Sources: F-03, A-03; AS-02.
- **SC-03:** Response loss and restart before local commit retain the original identity/key/parameters and avoid another checkout. Unavailable Stripe ends within the configured budget and exposes inspectable unresolved work. Sources: A-06/A-07/A-08.
- **SC-04:** Authenticated status/history distinguishes unpaid/pending, unresolved, and confirmed payment; creation, decline, cancellation/abandonment, timeout, and browser return do not falsely confirm payment or terminate the entire order. Sources: F-02/F-05; A-02; AS-03.
- **SC-05:** Business changes and their append-only history commit together, with no partial state/history under injected failure; concurrent creation preserves database invariants. Sources: F-08/E-09/Q2; AS-04/A-18.
- **SC-06:** Unauthorized/invalid inputs are rejected and feature response/log/history paths exclude prohibited sensitive data. Sources: A-12/E-02/Q5.
- **SC-07:** An old unresolved creation cannot silently become a new checkout by unsafe replay beyond the idempotency retention guarantee. Sources: F-07/A-11/Q3.
